# Автотесты курса: ДЗ 1–10

Основная инструкция подключения — в [корневом README](../README.md).
Студент один раз добавляет `ci-example.yml` в `.github/workflows/course.yml`.
Для каждого задания открывает PR с номером ДЗ в заголовке: например, `ДЗ 3` или `task3`.
Имя ветки произвольное; при изменении заголовка PR проверка запускается повторно.
Результат находится в Checks его PR. Параметры CI менять не нужно.

## Запуск

```bash
cd ~/code/go-courses/autotests
python3 -m pip install -r requirements.txt

# Автоматически определить ДЗ и структуру:
python3 scripts/ci.py --repo ~/code/student-homework --pr-title "ДЗ 7"

# Локальный запуск указанного задания (номер или taskN):
./scripts/check.sh 3 ~/code/student-homework --package cmd/server
./scripts/check.sh 6 ~/code/student-homework/task6 --report reports/task6.json
./scripts/check.sh 7 ~/code/student-homework --report reports/task7.json

# Проверка корректности тестового инструмента:
make check
make test

```

Зависимости: Go 1.26.4+, Python 3.9+, Git, PyYAML из `requirements.txt`.
Для ДЗ 5–10 обязательны работающие Docker и Docker Compose. Если Docker недоступен,
запуск завершается ошибкой. Отсутствие инфраструктуры не считается успешной проверкой.

## Требования к запуску

- `MOVIE_BASE_URL` — базовый URL фильм-стенда, путь запроса `/{id}/info.0.json`.
- `HTTP_ADDR` — адрес HTTP-сервера (ДЗ 3–8).
- `DATABASE_URL` — PostgreSQL DSN (ДЗ 5–8).
- `REDIS_ADDR` — `host:port`, без пароля (ДЗ 6–8).
- `KAFKA_BROKERS` — адреса брокеров через запятую (ДЗ 7–8).
- С ДЗ 7 точки входа располагаются в путях с `catalog`/`downloader` в названии.
  Поддерживаются как один общий Go-модуль, так и два отдельных.
- Запуск без обязательных CLI-аргументов; относительные пути к конфигурационным файлам читаются из каталога Go-модуля.
- С ДЗ 5 сервис должен применить SQL-миграции/подготовить схему при старте до синхронизации.
  SQL-миграции должны быть в репозитории. Таблица фильмов содержит `title`.
  Стенд и тестовые данные возвращают только `id`, `title`, `year`, `director`, как API kinosearch.
  Описание, актёры, жанры и таблицы связей не требуются.
- Поиск: `GET /search?q=...` возвращает JSON-массив фильмов. Проверяются отдельные слова
  из `title` и `director`; логика AND/OR для многословных запросов не проверяется.
- ДЗ 6: `q` регистронезависим, пробелы по краям игнорируются; отсутствующий или пустой
  `q` даёт 400 с описанием. Нет совпадений → `[]`. Проверяются точные id без дублей и лишних результатов.
  Индекс строится по всем фильмам из PostgreSQL до первого запроса и хранится без TTL.
  Кэш полного ответа имеет TTL 3600 секунд; ключи и структуры Redis свободные.
- ДЗ 8: `GET /` возвращает HTML-форму с полем `q`; метод GET, action указывает на HTML-результаты.
- Compose в корне решения: `compose.yaml`, `compose.yml`, `docker-compose.yml` или `docker-compose.yaml`.
  В именах двух сервисов есть `catalog`/`downloader`; они собираются через `build`.
  У catalog опубликован HTTP-порт. Адрес тестового сервера задаётся проверкой через `MOVIE_BASE_URL`.
- ДЗ 9: Deployment для каждого сервиса; имена содержат `catalog`/`downloader`, для catalog указано `replicas >= 2`.
- ДЗ 10: `/metrics` отдаёт Prometheus text format с числовыми значениями; точные имена метрик свободные.
  JSON-лог запроса содержит `level`, `msg` и непустой request/correlation id.

HTTP-контракт: `/load-movies?from=N&to=M` → JSON-массив; `/last-movie` → JSON-объект.
Поля: `id` (число), `title` (строка), `year` (число), `director` (строка).
Неверные параметры HTTP дают 400 с непустым описанием. Swagger доступен на `/swagger/index.html`.
ДЗ 2: `--from`, `--to`, `--workers` (10), `--timeout` (5).
Вывод успешного фильма: `id — title — year — director`, порядок строк свободный.

Требования к переменным окружения и путям необходимо включить в условия заданий,
чтобы CI не требовал ручных настроек на каждом задании.

## Интерпретация результатов и ограничения

Для ДЗ 6 проверка очищает отдельный временный Redis и перезапускает приложение:
без индекса холодный поиск не должен успешно возвращать фильмы через SQL/перебор.
Допускаются пустой результат, HTTP-ошибка или восстановление индекса перед ответом.
После перезапуска проверяется поиск по ранее загруженным данным. Проверка источника
данных меняет название фильма в PostgreSQL и делает некэшированный запрос по режиссёру.
Для проверки TTL удаляются ключи с истечением срока жизни (кэши), но сохраняется индекс;
затем проверяется новый часовой ключ и доступность ответа при остановленном PostgreSQL.
Регрессии этих проверок находятся в `tests/test_task6.py`.

Базовые проверки ДЗ 7–8, 9 и 10 дополнительно описаны в `scripts/task78.py`,
`scripts/task9.py` и `scripts/task10.py`. Их небольшие регрессионные тесты:
`tests/test_task7_8.py`, `tests/test_task9.py`, `tests/test_task10.py`.
Для ДЗ 8 HTML-поиск проверяется по названию и режиссёру. Для ДЗ 9–10 проверяются
список фильмов, последний фильм со всеми четырьмя полями и JSON-поиск.

Успешный результат подтверждает прохождение перечисленных проверок.
Для ДЗ 7–10 используются базовые сценарии: обычная синхронизация, HTTP API,
поиск по названию/режиссёру и проверки, относящиеся к текущему заданию.
Остановка зависимостей, повторная доставка Kafka, нагрузка и отказ реплик
не входят в эти автопроверки. Готовые решения ДЗ 6–10 в репозиторий не добавляются;
тесты проверяющего инструмента используют небольшие данные и моки.
Прохождение автотестов не означает выполнение всех критериев задания:
не проверяются gRPC, все частичные ошибки, Kafka retry/DLQ и offset при ошибке БД,
реальный запуск Kubernetes и качество панелей Grafana. Проверка Swagger подтверждает только доступность HTML-страницы.
Анализ импортов проверяет базовые ограничения между слоями; архитектуру приложения необходимо оценить на ревью.

Для ДЗ 8 преподавательские тесты не добавляются к студенческому профилю покрытия.
Покрытие агрегируется по числу операторов Go во всех модулях решения, строго >70%.
Сгенерированный код пока не исключается из общего покрытия.

Исходное решение копируется во временную папку. Выполнение кода при этом не изолируется:
запускайте сторонние решения
в одноразовом окружении без секретов. Итоговую приёмку делайте на конкретном SHA студента и версии тестов.
JSON-отчёт содержит результаты и идентификаторы проверенных коммитов. Незакоммиченные изменения в SHA не отражаются.
