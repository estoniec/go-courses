### Redis: поиск и кэширование

Продолжите сервис из [ДЗ 5](task5.md): добавьте обратный индекс и кэш поисковых ответов в Redis. PostgreSQL остаётся основным хранилищем фильмов. Сохраняются HTTP/gRPC API, миграции, автоматическая синхронизация при старте и отсутствие дублей при повторной загрузке.

### Данные для поиска

Фильм запрашивается по адресу `{MOVIE_BASE_URL}/{id}/info.0.json`. Контракт соответствует [kinosearch](https://github.com/vacmannnn/kinosearch/blob/fe95131b8651f8be9b42aad94602ad3e73c555db/internal/handler/get_movie.go):

```json
{
  "id": 1,
  "title": "Solaris",
  "year": 1972,
  "director": "Andrei Tarkovsky"
}
```

Стенд возвращает только четыре поля: `id` и `year` — числа, `title` и `director` — строки. В PostgreSQL сохраняются все четыре поля, как в ДЗ 5. Обязательный поиск — по словам из **названия (`title`) и режиссёра (`director`)**. Идентификатор и год участвуют в хранении и ответах API, индексировать их не требуется.

`description`, `actors`, `genres` стенд не возвращает. Добавлять их хранение, таблицы связей, ручное заполнение или получать данные из других источников не нужно. Поиск по этим полям не требуется и на оценку не влияет. Новые SQL-миграции нужны только если этого требует ваша реализация; четырёх полей из ДЗ 5 достаточно.

### Обратный индекс

1. При старте подготовьте схему PostgreSQL и синхронизируйте фильмы со стендом.
2. Постройте в Redis индекс по **всем фильмам из PostgreSQL**, включая ранее загруженные: слово → набор id фильмов. Используйте слова из `title` и `director`.
3. Индекс должен быть готов до обработки поисковых запросов. Ключи индекса храните без TTL, отдельно от кэша ответов. Конкретные имена ключей и структуры Redis выбирайте сами.
4. После перезапуска с пустым Redis индекс должен восстановиться из PostgreSQL. Новые фильмы, загруженные при следующем старте, тоже должны попадать в индекс. Повторная индексация не должна создавать дубликаты результатов.

Для разбиения текста на слова используйте последовательности букв и цифр; приводите слова к нижнему регистру. Пустые элементы пропускайте. Поиск регистронезависимый, по целым словам, без обязательной морфологии и поиска по подстроке. Для нескольких слов можно выбрать AND или OR; опишите выбор в README своего решения.

### HTTP-контракт

Добавьте `GET /search?q=...`:

- Уберите пробелы по краям `q`. Отсутствующий, пустой или состоящий только из пробелов `q` → HTTP 400 с непустым описанием ошибки.
- Найдите id по обратному индексу Redis, затем прочитайте сами фильмы по этим id из PostgreSQL. Поиск перебором каталога в памяти или SQL-запросом вместо Redis не подходит.
- Успешный ответ → HTTP 200 и JSON-массив фильмов с полями `id`, `title`, `year`, `director`. Порядок фильмов произвольный, дубликатов и посторонних фильмов быть не должно.
- Если совпадений нет, верните `[]`, а не `null` и не 404.

Примеры для данных выше: `q=Solaris`, `q=Andrei`, `q=Tarkovsky` находят фильм 1; `q=SOLARIS` тоже находит фильм 1.

### Кэш ответов

Кэшируйте в Redis полный успешный ответ `/search` с TTL **3600 секунд** с момента записи. Повторный запрос с тем же `q` должен возвращать ответ из Redis без чтения PostgreSQL, в том числе когда PostgreSQL временно недоступен. Не продлевайте TTL при чтении. Для разных запросов используйте разные ключи. Ошибки 400/500 не кэшируйте.

При построении нового индекса сбрасывайте старый кэш ответов, чтобы новые фильмы были видны после синхронизации. Изменения фильмов во время работы сервиса, кроме описанной синхронизации при старте, в этом ДЗ не требуются.

### Конфигурация и запуск

Сервис читает переменные окружения:

- `MOVIE_BASE_URL` — базовый URL фильм-стенда;
- `HTTP_ADDR` — адрес HTTP-сервера;
- `DATABASE_URL` — PostgreSQL DSN;
- `REDIS_ADDR` — адрес Redis в формате `host:port`, без пароля в тестовом окружении.

Сохраняются значения по умолчанию для `MOVIE_BASE_URL` и `HTTP_ADDR` из ДЗ 3; переданное окружение имеет приоритет. Запуск — без обязательных CLI-аргументов, из каталога Go-модуля. Приложение должно содержать один Go-модуль и одну точку входа `package main`.

В README решения опишите запуск PostgreSQL, Redis и приложения, применение миграций, переменные окружения, структуру индекса, выбранную логику многословного поиска и примеры запросов.

### Критерии оценивания

6 баллов — Все требования выполнены: индекс строится автоматически по названию и режиссёру, восстанавливается из PostgreSQL, поиск находит id через Redis и читает фильмы из PostgreSQL. Ответы кэшируются на час и доступны из кэша без PostgreSQL. Конфигурация читается из окружения, запуск описан в README. Сохранены требования ДЗ 5.

5 баллов — Основной сценарий выполнен, но есть небольшой недочёт: например, срок жизни кэша отличается от часа или неполно описан запуск. Оба обязательных поля участвуют в поиске, фильмы читаются из PostgreSQL.

4 балла — Поиск через обратный индекс Redis работает, но отсутствует кэширование ответов, индекс не охватывает название или режиссёра, не строится автоматически при старте или не восстанавливается по ранее загруженным фильмам.

3 балла — Ручка поиска есть, но Redis используется только для кэша, а поиск выполняется перебором фильмов или SQL-запросом. Либо индекс строится, но найденные id некорректно преобразуются в результаты из PostgreSQL.

0–2 балла — Работа не сдана, код не компилируется или сервис не запускается. Либо поиск не работает, Redis не используется или ручка `/search` возвращает заглушки.

Отметка за задание снижается при более поздней сдаче задания (1 балл за каждые 2 недели опоздания).
