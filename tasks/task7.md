### Kafka: разделение на два сервиса

Нужно разделить приложение на два сервиса:

- `catalog-service` — общается с пользователем, хранит фильмы в PostgreSQL, использует Redis для поиска и кэша.
- `downloader-service` — скачивает фильмы с внешнего фильм-стенда.

Сервисы должны общаться асинхронно через Kafka.

Топики:

- `movie_download_tasks` — задачи на скачивание фильмов.
- `movie_downloaded` — скачанные фильмы.

Как это работает:

1. `catalog-service` на старте смотрит максимальный id фильма в PostgreSQL.
2. `catalog-service` отправляет в Kafka задачу `NeedToDownload` с этим id.
3. `downloader-service` читает задачу и скачивает со стенда все фильмы от `id + 1` до последнего доступного.
4. Каждый скачанный фильм `downloader-service` отправляет в Kafka.
5. `catalog-service` читает скачанные фильмы из Kafka и сохраняет их в PostgreSQL.

HTTP/gRPC API для пользователя остаётся в `catalog-service`.

### Контракт фильма и поиск

Используйте тот же [API kinosearch](https://github.com/vacmannnn/kinosearch/blob/fe95131b8651f8be9b42aad94602ad3e73c555db/internal/handler/get_movie.go), что в ДЗ 5–6: `GET {MOVIE_BASE_URL}/{id}/info.0.json` возвращает только четыре поля:

```json
{"id": 1, "title": "Solaris", "year": 1972, "director": "Andrei Tarkovsky"}
```

`id` и `year` — числа, `title` и `director` — строки. Для отсутствующего фильма стенд возвращает 404. Описание, актёры и жанры не нужны: получать или заполнять их вручную не требуется.

Передавайте скачанные фильмы через Kafka и сохраняйте все четыре поля в PostgreSQL. Формат задачи и сообщения с фильмом выберите сами и опишите в README; оба сервиса должны использовать один контракт. Для пустой БД начальный максимальный id равен 0.

Сохраняются пользовательские ручки `/load-movies`, `/last-movie`, `/search?q=...` из предыдущих ДЗ. Поиск обязателен по названию и режиссёру. После сохранения фильма из Kafka обновляйте индекс Redis и сбрасывайте устаревший кэш поиска, чтобы новый фильм находился без перезапуска сервисов.

### Конфигурация

Сервисы должны читать конфигурацию из переменных окружения:

- `MOVIE_BASE_URL` — базовый URL внешнего фильм-стенда, используется `downloader-service`;
- `HTTP_ADDR` — адрес HTTP-сервера, используется `catalog-service`;
- `DATABASE_URL` — строка подключения (DSN) к PostgreSQL;
- `REDIS_ADDR` — адрес Redis в формате `host:port`;
- `KAFKA_BROKERS` — адреса брокеров Kafka, перечисленные через запятую.

Сохраняются требования предыдущих ДЗ к приоритету значений из окружения, значениям по умолчанию для `MOVIE_BASE_URL` и `HTTP_ADDR` и запуску без обязательных CLI-аргументов.

Точки входа сервисов должны находиться в каталогах, содержащих `catalog` и `downloader` в имени, например `cmd/catalog-service` и `cmd/downloader-service`. Можно использовать один Go-модуль или отдельный модуль для каждого сервиса.

Повторная обработка одного и того же фильма не должна создавать дубликаты в БД. Offset сообщения со скачанным фильмом должен коммититься только после успешной записи в PostgreSQL.

Для временных ошибок нужно сделать retry. Сообщения, которые не удалось обработать после нескольких попыток, должны попадать в DLQ.

Оба сервиса должны быть спроектированы по принципам чистой архитектуры из предыдущего ДЗ.

### Критерии оценивания

6 баллов — Приложение разделено на catalog-service и downloader-service с соблюдением чистой архитектуры. catalog-service отправляет NeedToDownload с максимальным id из БД в movie_download_tasks, downloader-service скачивает новые фильмы и публикует их в movie_downloaded. catalog-service сохраняет фильмы без дублей и коммитит offset только после успешной записи в PostgreSQL. Для временных ошибок есть retry, после исчерпания попыток сообщения попадают в DLQ. HTTP/gRPC API, поиск и кэш работают в catalog-service. Конфигурация читается из окружения, в README описан запуск обоих сервисов и Kafka.

5 баллов — Весь обмен через Kafka, сохранение без дублей, порядок коммита offset, retry и DLQ работают. Есть небольшой недочёт в документации или разделении слоёв, который не нарушает ответственность сервисов.

4 балла — Два сервиса обмениваются задачами и фильмами через Kafka, основной сценарий работает, но отсутствует retry или DLQ. Либо сервисы сильно связаны и нарушают чистую архитектуру при сохранённом разделении ответственности.

3 балла — Разделение на сервисы выполнено частично, реализовано только одно направление обмена через Kafka или нарушена надёжность обработки: появляются дубли либо offset коммитится до записи фильма в БД, создавая риск потери данных.

0–2 балла — Работа не сдана, сервисы не запускаются или обмен через Kafka не реализован. Либо вместо обмена сообщениями используются заглушки и скачанные фильмы не доходят до PostgreSQL.

Отметка за задание снижается при более поздней сдаче задания (1 балл за каждые 2 недели опоздания).
